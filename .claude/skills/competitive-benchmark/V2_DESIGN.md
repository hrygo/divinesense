# Competitive Benchmark v2.0 设计方案

> 从 "Issue 生成器" 重构为 "洞察引擎"

---

## 一、核心理念重构

### 1.1 当前问题诊断

| 问题 | 根本原因 | 后果 |
|:-----|:---------|:-----|
| 追随者心态 | 假设"竞品有→我也要有" | 丧失差异化思考 |
| 表面化分析 | 只看"有什么功能" | 缺失"为什么成功" |
| 伪精确评分 | 技术契合度×权重 | 掩盖真实复杂性 |
| 产出单一 | 只生成 Issue | 丢失战略洞察 |

### 1.2 新的核心理念

```
竞品分析的本质是：
理解用户价值 → 抽象成功模式 → 创造性转化

而非：
发现功能差距 → 创建追赶 Issue
```

**新的定位**：
- 不再是"OpenClaw 追随者"
- 而是"AI 个人知识管理领域的洞察者"
- OpenClaw 是一个**参考样本**，而非**目标**

## 二、新的系统提示词

### 2.1 v2.0 System Prompt

```yaml
name: competitive-benchmark
version: 2.0.0
system: |
  你是 AI 产品领域的洞察专家，专注于"个人知识管理 + AI 代理"赛道。

  **你的独特视角**：
  - 你不是在"追赶竞品"，而是在"理解赛道"
  - 你不只看"有什么功能"，而是问"解决了什么问题"
  - 你不只做"差距分析"，而是做"价值溯源"

  **核心方法论：价值三问**
  1. **问题本质**：这个功能到底解决了用户的什么痛点？
  2. **价值来源**：为什么用户认为它有价值？（而非技术实现）
  3. **创造性转化**：同样的价值，我们能否用更好的方式实现？

  **动态适应原则**：
  - 多源数据：代码 + Issue + Release + 用户讨论
  - 多维分析：功能 + 架构 + 用户价值 + 差距化
  - 渐进披露：先给洞察，再给建议，最后才是任务

  **产出优先级**：
  1. 洞察报告（Insight Report）- "为什么"
  2. 战略建议（Strategy Recommendation）- "做什么"
  3. 差距化机会（Differentiation）- "凭什么赢"
  4. 实施任务（Issue）- "怎么做"（仅当确定要做时）

  **行为约束**：
  - 拒绝"跟随者心态"：不因为竞品有就认为我们需要有
  - 拒绝"技术中心主义"：技术相似度不等于价值
  - 拒绝"伪精确评分"：避免用数字掩盖复杂性
  - 拥抱"不确定性"：用 AskUserQuestion 处理模糊判断
```

### 2.2 与 v1.3 对比

| 维度 | v1.3 | v2.0 |
|:-----|:-----|:-----|
| 定位 | OpenClaw 追随者 | 赛道洞察者 |
| 目标 | 发现功能差距 | 理解成功模式 |
| 方法 | 技术契合度评分 | 价值三问 |
| 产出 | Issue 列表 | 洞察报告 + 战略建议 |
| 数据源 | GitHub API + 代码扫描 | 多源数据 + 用户讨论 |

### 3.3 阶段 1-2：问题本质与价值溯源

**新的分析框架**：

```yaml
功能分析模板:
  feature:
    name: "会话修剪"

  # 问题本质（而非功能描述）
  problem_essence:
    user_pain: "AI 对话历史无限增长导致检索变慢、成本升高"
    root_cause: "上下文窗口与记忆成本的矛盾"
    solved_by: "主动修剪低价值对话，保留高价值摘要"

  # 价值溯源（而非技术评分）
  value_source:
    primary: "成本控制（API 调用费用）"
    secondary: "响应速度（更少上下文）"
    user_perceived: "无明显体验下降"

  # 成功要素（可迁移）
  success_factors:
    - "智能识别低价值对话"
    - "保留结构化摘要"
    - "用户可控的修剪策略"
```

### 3.4 阶段 3-4：模式抽象与创造性转化

**新的评估维度**：

```yaml
创造性转化分析:
  feature: "会话修剪"

  # 底层模式（跨技术栈）
  underlying_pattern:
    name: "记忆成本管理"
    principle: "有限资源下的价值最大化"
    applicable: true  # 跨技术栈适用

  # 我们的独特优势
  our_differentiation:
    divineSense_strength: "单二进制 + SQLite 本地存储"
    opportunity: "本地记忆管理，零 API 成本"
    strategy: "不复制其修剪，而是优化本地存储结构"

  # 战略判断
  strategic_decision:
    should_we_do: "是，但不同方式"
    approach: "本地索引优化 + 增量清理"
    priority: "P1（差异化优势）"
```

```markdown
## 一、问题本质分析

### 1.1 用户痛点图谱

```
核心矛盾：AI 记忆的无限增长 vs 有限资源
├── 成本维度：API 调用费用
├── 性能维度：上下文窗口限制
├── 体验维度：检索精度下降
└── 隐私维度：数据留存担忧

OpenClaw 的解决方式：主动修剪
我们的机会：本地零成本存储
```

### 1.2 功能-问题映射表

| OpenClaw 功能 | 解决的问题 | 用户价值来源 | 可迁移性 |
|:-------------|:-----------|:-------------|:---------|
| 会话修剪 | API 成本 | 成本控制 | ⚠️ 不同场景 |
| 插件系统 | 可扩展性 | 可能性 | ✅ 高 |
| 多渠道集成 | 用户触达 | 便利性 | ❌ 不同定位 |
```

## 十、Human-in-the-Loop (HITL) 设计

### 10.1 交互哲学

```yaml
核心原则:
  - AI 是"思考伙伴"，而非"全自动工具"
  - 人类负责判断，AI 负责分析和选项
  - 关键决策点必须有人类确认

交互时机:
  1. 分析方向确认（"重点分析哪个维度？"）
  2. 模式验证（"这个归纳对吗？"）
  3. 战略判断（"我们应该做这个吗？"）
  4. 优先级排序（"哪个更重要？"）
```

### 10.2 交互式工作流

```
传统模式（v1.3）:
  输入 → AI 分析 → 输出 Issue（无确认）

HITL 模式（v2.0）:
  输入 → AI 初步分析 →
    ├─人类确认方向 → 深度分析 →
    ├─人类修正假设 → 重新分析 →
    └─人类直接判断 → 跳到结论 →
  输出（人类参与共同创造）
```

### 10.3 关键交互点设计

#### 交互点 1：分析维度选择

```yaml
触发条件: 发现多个值得深入的方向

交互示例:
  AI: "发现了 3 个值得深入的方向：
      1. 会话修剪（成本优化模式）
      2. 插件系统（可扩展性模式）
      3. 多渠道集成（用户触达模式）

      你希望我重点分析哪个？还是全部分析？"

  人类选项:
    a) 全部分析
    b) 重点分析 X
    c) 先分析 X 和 Y
    d) 给我推荐

  AI 根据: 继续 → 针对性深入分析
```

#### 交互点 2：模式验证

```yaml
触发条件: 抽象出新的模式或假设

交互示例:
  AI: "我注意到一个模式：
      OpenClaw 的'会话修剪'、'记忆压缩'、'摘要提取'
      本质上都是同一个底层模式：

      【记忆成本管理】→ 在有限资源下最大化信息价值

      这个归纳对吗？你有没有不同的理解？"

  人类选项:
    a) 同意，继续
    b) 部分同意，我的看法是...
    c) 不同意，我认为...
```
